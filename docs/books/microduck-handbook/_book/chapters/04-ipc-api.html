第四章：IPC 是服务之间的公共语言

MicroDuck 把本机服务放在独立进程里，因此需要一种稳定的本地通信方式。duck-ipc-proto 定义 JSON-RPC 2.0 消息，一个 Unix socket 上每行一个 JSON 对象。协议 crate 刻意保持轻量，只依赖序列化和版本信息，这样 btd 或 robotd 不会因为共享协议而拖入更新器的 HTTP、压缩和密码学依赖。

一条本机请求长什么样

JSON-RPC 请求包含协议标识、方法名、参数和请求 ID；服务返回同一 ID 的结果或错误。每行一条消息使 socket 流能够被简单地逐条解析，也让调试时可以直接记录和检查边界。

{"jsonrpc":"2.0","id":1,"method":"robot.move",
 "params":{"vx":0.12,"vy":0.0,"vyaw":0.4}}

这类请求表达的是“以一定速度移动”的意图，不是“第 3 个舵机转到 0.6 弧度”。后者会绕过策略和运动安全，难以与行走中的状态协调。

方法按功能域命名

常见命名空间包括 robot.、policy.、detector.、tof.、media.、net.、system.、pad. 和 chorale.*。前缀帮助读者看出状态与行为归哪个服务所有。相同的协议消息可以来自本地 CLI、BLE 桥接或 WebRTC 控制通道，但入口都必须被限制为该客户端有权调用的子集。

robot.move、robot.stop、robot.look 和 robot.state 是移动与状态控制的典型例子。policy.check 和 policy.install 属于策略组件获取；robot.loadPolicy 则告诉运动服务哪个策略槽位应启用。区分“下载一个文件”和“让运行中的控制器使用该文件”，可以避免把存储操作与实时切换混成一个动作。

版本和兼容性

共享协议带有 API 版本，方法演进要考虑不同服务的重启顺序。新增字段应优先保持可选或带默认值的兼容行为；如果能力确实不可用，应该明确报“方法不存在”或“参数不支持”，而不是让客户端猜测某个服务版本。

Unix socket 路径、运行目录和服务身份也属于合同的一部分。duck-ipc-proto/src/lib.rs 中可以找到各 socket 的默认路径与方法常量。阅读某个 API 时，同时搜索定义、服务端分派和调用方，不要只看 CLI 的命令行名字。

安全边界在入口处

btd 和远程控制不应该暴露所有内部方法。它们要验证路由、参数和调用者权限，再转发到本地服务。服务之间使用 Unix socket 的权限、Linux peer credentials 和 systemd 用户隔离提供额外保护。设计新功能时，先确认它应从本机 CLI、BLE、WebRTC 的哪一个入口开放，再给相应入口增加受限的路由。
